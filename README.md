# rpa-asp-governance-cirp2027

ASP-based declarative governance core for RPA autonomous decision-making in
manufacturing: code and synthetic test data for the paper *A Two-Layer RPA
Architecture with Declarative Governance for Auditable Autonomous
Decision-Making in Cyber-Physical Manufacturing Systems* (Patil and Fatahi
Valilai, CIRP CMS 2027).

**All test events are synthetic.** They are constructed scenarios that test
the governance specification. They are not measurements from a cobot cell
or a production scheduler, and the grade mappings in `adapters/` are
defined by the authors.

## Layout

```
core/governance_core.lp          four domain-independent rules (R1-R4)
core/priority_matrix.lp          4x4 matrix facts and thresholds (policy lives here)
adapters/cobot_adapter.lp        cobot task reallocation adapter
adapters/scheduling_adapter.lp   sustainable scheduling exception adapter
test_events/cobot/               events CB-01 .. CB-07
test_events/scheduling/          events SS-01 .. SS-07
run_experiments.py               reproduces every number in the paper
requirements.txt                 pinned solver version
results/results.json             machine-readable output of the last run
results/verification.md          human-readable report of the last run
results/timing_reported_in_paper.json   the decision-time run quoted in the paper (fixed record)
results/events_table_rows.tex    event-table rows of the paper (generated by the script)
```

## Reproduce

```bash
pip install -r requirements.txt   # clingo 5.8.2
python run_experiments.py   # prints a report, ends with "ALL CHECKS PASSED"
```

The script runs seven experiments:

| | What it does |
|---|---|
| E1 | 14 events through the adapters; compared with outcomes declared in the script before running, and with an independent Python reference implementation |
| E2 | the core alone on 16 (C,U) pairs x 101 confidence scores under 36 threshold settings (58,176 decisions) vs the reference implementation |
| E3 | one line of `priority_matrix.lp` edited in a scratch copy (theta_p 3 -> 4); SHA-256 of every file compared before and after |
| E4 | statement counts via the clingo parser (core 23, each adapter 10) |
| E5 | fault injection: four broken variants of the core, checked against the 14 events and against E2 |
| E6 | decision time: 100 timed runs per event (after 20 warm-up runs), each with a new solver instance, core + adapter loading, grounding and solving; written to `results/timing_latest.json` |
| E7 | matrix-cell test: a safety-critical event with ample time is autonomous under the shipped matrix and escalates after changing the single fact `matrix(4,1,2)` to `matrix(4,1,3)` |

Run a single domain with the solver directly:

```bash
python -m clingo core/governance_core.lp core/priority_matrix.lp \
    adapters/cobot_adapter.lp test_events/cobot/cobot_events.lp
```

E6 depends on the machine. `results/timing_reported_in_paper.json` is the run quoted in the paper;
the paper also quotes the spread over three repeated runs on that machine (medians 0.66 to
0.77 ms, maxima 1.9 to 5.0 ms). Each new run of the script writes `results/timing_latest.json`
(git-ignored); quote your own numbers if you re-measure. `results.json` and
`verification.md` are deterministic and identical on every run.

## Conventions

- Confidence is an integer score in [0,100] because clingo has no floats.
  Thresholds: `theta_k = 60`, `theta_d = 1` (Routine), `theta_p = 3` (Priority).
- Tiers: 1 Routine, 2 Elevated, 3 Priority, 4 Critical.
- Escalation reasons are arguments of the head atoms of R2 and R3
  (`escalate(E, low_confidence)`, `escalate(E, high_priority)`), so the audit
  trail is part of the answer set. An event may carry both reasons.
